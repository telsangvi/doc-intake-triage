Document Intake Triage

Turn a pile of documents into a queue you can work through

A benefits office gets applications and the papers that come with them. Someone has to read every one, pull out the details, spot what's missing, and decide what to do next. This does that first pass for you.

You drop in the documents. For each one, the system reads it, pulls out the details that matter, and works out whether it's ready to move on — or needs something first.

Then you get one queue, with every item already sorted and labelled with the reason. You stay in charge of what happens next.

It sorts and flags. It never decides who gets benefits.
The problem

What changes

The slow part isn't the decision — it's the reading. Every document has to be opened, understood, and checked before anyone can act on it.

Doing it by hand

  • Open every document and read it end to end
  • Retype the same details into the case system
  • Notice later that something required was missing
  • The applicant waits while it gets chased
  • Poor scans are a guess — no signal about what's trustworthy

With the queue

  • Drop the documents in and walk away
  • Details come out already typed and ready to check
  • Missing fields are caught before anyone reviews the case
  • Every item says what's wrong, in plain words
  • Unclear scans are flagged for a person, not guessed at

The three outcomes

What each one means for you

Ready to process

Everything the policy asks for is present, and the system read it clearly. Nothing is in doubt.

What you doMove it on. It doesn't need a second pair of eyes.
Ask the applicant

A required detail isn't in the document at all — the form is blank where it should say something.

What you doSend it back. The system names exactly what's missing, so the request is specific.
Needs a person

The detail is there, but it can't be trusted — a bad scan, handwriting, or placeholder text where a value should be.

What you doCheck it yourself. The system won't guess when it isn't sure.
Why the last two are kept apart. A missing field is a problem with the applicant's paperwork — it goes back to them. An unclear field is a problem with the document — it goes to you. Treating those as the same thing is how systems end up either nagging applicants for things they already sent, or quietly guessing at values nobody can read.

case_003_application.txt Needs a person
The scan is poor — the name reads "???" and the date of birth says "unclear". Rather than guess, it's flagged for you.

Every item can explain itself. Alongside the reason, each item records which rule it applied — so if someone asks "why did this go back?" six months later, the answer is on the record, not in someone's memory.
Where it stops

What it will not do

This matters more than any feature. The system reads, sorts, and flags. Everything else stays with people.

It will not

  • Decide whether anyone gets benefits
  • Score, rank, or judge an applicant
  • Reject a case for missing paperwork
  • Invent a value it couldn't read
  • Overrule a caseworker's judgement

It will

  • Read every document the same way, every time
  • Say plainly what it found and what it couldn't
  • Hand anything uncertain to a person
  • Keep a record of which rule it applied
  • Get out of the way when you know better
